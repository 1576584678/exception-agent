## 二、背景与目标

### 2.1 背景

线上问题定位目前依赖「人找人」：客诉截图发到群里 → 有人猜是哪个服务 → 去日志平台手动搜 → 再去 GitLab 翻代码 → 找 DB 查数据。一次定位平均要跨 3 个系统、问 2 个人。

三类断点最耗时：

1. **截图到日志断点**：截图里只有一句报错文案，没有 traceId，靠人猜关键词。
2. **日志到代码断点**：知道报错在哪个服务，但不知道该看哪个文件、哪一行，也不知道这行最近被谁改过。
3. **代码到数据断点**：判断是数据脏了，但要人工拼 SQL 去查具体那条记录。

### 2.2 目标

把「截图/描述 → 原因 → 代码位置 + 提交人 → 具体数据」这条链路做成一次提交、一份报告。

| 指标           | 口径                 | 目标值（上线 3 个月）       |
| ------------ | ------------------ | ------------------ |
| MTTA（平均定位时长） | 提交分析 → 报告生成完成，P50  | ≤ 90 秒（P95 ≤ 5 分钟） |
| Top-1 归因采纳率  | 报告首条结论被人工标记「正确」的比例 | ≥ 60%              |
| Top-3 命中率    | 正确结论出现在前 3 条的比例    | ≥ 85%              |
| 证据挂载率        | 结论区中带可点击证据的结论占比    | 100%（硬指标）          |
| 数据定位成功率      | 数据类问题中给出具体记录的比例    | ≥ 70%              |
| 越权/泄露事件      | 跨项目读取、明文凭证外泄次数     | 0（硬指标）             |

> 口径说明：采纳率由报告页「结论是否正确」二选一标记统计，样本为该周期内已标记的报告；未标记不计入分母。

### 2.3 不做的事（本期明确不做）

- 不做自动修复、不自动改代码、不自动改数据（只给建议）。
- 不做线上实时告警接入（不与告警平台打通触发，只做人工提交）。
- 不做提交人绩效统计、不做「谁 bug 多」排行榜（见 14.2 风险 R-03）。
- 不做移动端。

## 三、名词与术语

| 术语              | 定义                                             |
| --------------- | ---------------------------------------------- |
| 项目（Project）     | 一组接入配置的集合：代码源 + 日志源 + 数据源 + 脱敏规则。分析任务必须归属于一个项目 |
| 证据（Evidence）    | 一条可回溯的原始材料，携带来源指针（日志查询条件+行号 / 文件:行 / SQL+结果行）  |
| 假设（Hypothesis）  | 对故障原因的一种候选解释，必须附带「验证所需证据」清单                    |
| 归因（Attribution） | 把问题定位到具体代码位置，并给出最后修改该行的提交与提交人                  |
| 证据链             | 从现象到结论的推导路径，每一步引用证据编号                          |
| 版本对齐            | 定位代码时使用「故障发生时间点对应的 commit」，而非分支最新 HEAD         |
| 出网闸             | 模型调用前的上下文构建器，只放行最小必要片段并全文脱敏、记录审计               |
| 置信度             | 高（日志+代码+数据三证）/ 中（两证）/ 低（单证或纯推测）                |

## 五、方案对比与选型

### 5.1 候选方案

- **方案 A：LLM 归因（检索 + 代码索引 + 假设验证）**——平台自建代码索引与日志检索，LLM 负责生成检索计划、生成假设、组织证据链，工具调用经白名单校验。
- **方案 B：纯检索式**——不做 LLM 归因，只做「关键词检索 + 相关代码行 + blame 链接」的拼装页。
- **方案 C：接现成 APM（如错误聚合类 SaaS）**——依赖其已有错误分组能力，人工排查。

### 5.2 对比

| 维度               | A LLM 归因        | B 纯检索式  | C 接现成 APM       |
| ---------------- | --------------- | ------- | --------------- |
| 能力上限             | 高（可给结论与修复建议）    | 低（只给线索） | 中（只覆盖已接入的运行时错误） |
| 实现成本             | 高（索引+流水线+安全）    | 低       | 低               |
| 数据安全             | 可控（可全内网 + 本地模型） | 最安全     | 差（日志出网）         |
| 上手成本             | 中               | 低       | 低               |
| 与「定位到人/定位到数据」匹配度 | 高               | 低       | 低               |

### 5.3 推荐

**选方案 A，并把方案 B 作为 A 的降级路径**：当模型不可用、项目开启「仅检索模式」、或置信度低时不强行给结论，直接退化为 B 的线索页。这样降级方案本身就是产品的一部分，不需要另做一套。

### 5.4 演进路径

| 版本  | 内容                                  | 进入条件          |
| --- | ----------------------------------- | ------------- |
| MVP | 单项目单日志源、文本/截图输入、代码归因、单库数据定位、报告      | —             |
| V2  | 前端仓库映射（截图路由 → 组件 → 前端代码）、MR 关联、多日志源 | MVP 采纳率 ≥ 50% |
| V3  | 相似问题复用（历史报告作为知识库）、自动生成修复 MR 草稿、告警触发 | V2 稳定运行 1 个月  |

## 六、用户角色与场景

| 角色      | 目标                       | 使用频率 |
| ------- | ------------------------ | ---- |
| 后端开发    | 接到报错后快速定位到文件行、确认是否自己的改动  | 高    |
| 值班 SRE  | 判断是代码问题、数据问题还是环境问题，决定转给谁 | 高    |
| 测试      | 复现后提交分析，拿到更精确的复现路径       | 中    |
| 技术支持/客服 | 提交客诉截图，拿到「可对外解释的原因」与处理时限 | 中    |
| 项目管理员   | 维护接入配置与脱敏规则、处理越权告警       | 低    |
| 审计员     | 查谁在什么时候看了哪个项目的日志与数据      | 低    |

### 6.1 主流程（后端开发视角）

1. 收到客诉截图，进入平台，选项目 → 上传截图，补一个发生时间。
2. 平台解析截图 → 生成检索计划并显示（可改关键词与时间窗）→ 开始分析。
3. 90 秒内出报告：结论一句话「订单详情页 NPE，因 couponService 返回空导致」。
4. 点结论下的证据 → 看到报错日志原文（脱敏后）与堆栈。
5. 点代码位置 → 跳转 GitLab 对应 commit 的对应行；旁边显示最后修改人、提交时间、commit message。
6. 若结论判定为数据异常 → 点数据定位 → 看到该记录字段快照，异常字段高亮。
7. 标记结论是否正确（正确 / 不正确 + 原因），可一键复制修复建议。

### M5 数据定位（数据类问题）

| 编号    | 需求         | 业务规则                                                                     | 验收要点（GWT）                                        |
| ----- | ---------- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| FR-24 | 主键抽取       | 从日志/堆栈/截图/用户输入中抽取业务主键（orderId/userId/xxxId）；**必须**经人工确认后才用于查询；抽不到时提示用户补填 | Given 抽取到 2 个候选主键 When 展示 Then 需用户勾选确认，未确认不执行查询  |

| FR-28 | 修复建议（不改数据） | 输出建议动作与影响行数估算，附手写 SQL 模板供人工在其工具中执行；平台**禁止**提供任何写操作入口                     | Given 报告含修复建议 When 用户点击 Then 仅复制 SQL 文本，平台不执行    |
| FR-29 | 数据定位失败降级   | 连接失败/超时/无权限时，输出「建议核查的表 + 主键 + SQL 模板」，状态标为「未完成」而非「失败」                    | Given DB 不可达 When 分析完成 Then 报告仍产出，数据章节标注未完成原因    |

### M6 报告

## 九、业务流程与状态

### 9.1 分析任务状态机

状态集合：`解析中 → 计划确认 → 采集中 → 归因中 → 数据核查中 → 出稿中 → 已完成 / 部分完成 / 失败 / 已取消`

| 当前状态 | 触发事件 | 迁移到 | 条件 / 说明 |
|---|---|---|---|
| 解析中 | 解析成功 | 计划确认 | 抽出 ≥1 个可用字段 |
| 解析中 | 解析失败 | 失败 | 提示补充文本描述，可重试 |
| 计划确认 | 用户确认/修改 | 采集中 | 未确认不自动进入采集 |
| 采集中 | 证据数 = 0 | 部分完成 | 输出「未检索到日志」+ 扩大窗口建议 |
| 采集中 | 证据数 > 0 | 归因中 | — |
| 归因中 | 定位成功 | 数据核查中 | 结论类型为「数据异常」时进入；否则直接出稿 |
| 归因中 | 定位失败 | 出稿中 | 结论类型 = 无法判定，输出线索清单 |
| 数据核查中 | 查询成功/降级 | 出稿中 | 失败也前进，标注未完成 |
| 出稿中 | 完成 | 已完成 | — |
| 任意阶段 | 超时（>5min） | 部分完成 | 后台续跑，完成后转已完成 |
| 任意阶段 | 用户取消 | 已取消 | 保留已采集证据（TTL 内） |

> 关键约束：状态单向流转，**禁止**从「已完成/部分完成」回跳到执行态（重跑生成新任务 ID）。

### 9.2 主流程

```
提交（截图/文本 + 补充字段）
  → 解析与脱敏 → 字段校对（人工确认）
  → 检索计划（可编辑）→ 并行采集日志（预算约束）
  → 归一 + traceId 串联 + 去噪
  → 生成 1~3 个候选假设，每个附验证计划
  → 代码定位（符号/错误码/文案）→ 版本对齐 → blame → 提交人
  → 若数据类假设：主键确认 → 模板化只读查询 → 字段快照对比
  → 报告（结论挂证据 + 置信度 + 建议 + 未验证项）
  → 反馈标记（正确/不正确）
```

### 10.3 指标口径

| 指标 | 计算式 | 周期 |
|---|---|---|

| MTTA | run 创建到 status=已完成 的时长，取 P50/P95 | 周 |
| 数据定位成功率 | 数据类结论中 dataProbe 状态=成功 的占比 | 周 |
| 降级率 | degradation_triggered 次数 ÷ analysis_submitted 次数 | 周 |

### 11.2 安全基线（六条硬约束，不可通过配置关闭）

1. 凭证只存引用，平台任何页面/接口**禁止**返回明文。
2. 三类外部资产（Git / 日志平台 / DB）统一只读；DB 必须表白名单 + 列黑名单。
3. 脱敏三闸全程生效，内置规则不可关闭。
4. 模型输出不得直接执行为工具调用，工具参数必须过 schema 校验。
5. 读取文件路径限定在已配置仓库根目录内，排除清单强制生效。
6. 审计日志不可删改，保留 ≥180 天；跨项目访问一律 403 + 记审计。
